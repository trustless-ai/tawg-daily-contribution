# ERC-8281: Observation Commitment Protocol (OCP)

## Summary

ERC-8281, known in the group as **OCP** (Observation Commitment Protocol), provides a minimal event-based commitment for off-chain observations: record a digest on-chain and verify it later by recomputation. It is the EVM-native instance of the base observation → digest → on-chain commitment → verify-inclusion primitive.

## Status

The org implementation was verified. No canonical normative source is registered, so the page does not assert an accepted ERC specification.

## Motivation

An observation can remain off-chain while its existence and integrity at a given chain position remain independently checkable.

## Architecture

An observer hashes an artifact, records the digest, and emits an event. A verifier later recomputes the digest and matches the event and chain position. The recompute→compare→confirm invariant is the foundational contribution of this primitive across the TAWG ERC stack.

## Interfaces

The current interface exposes a digest-recording entry point and an event carrying the digest and committer. It deliberately avoids an on-chain artifact store.

## State machine

The flow is append-only: compute, record, and independently verify. Any revocation or temporal-bound extensions are separate profiles, not part of this registered base implementation.

## Implementation

The org source treats the event log as the public ledger and keeps the observation itself private or externally stored. The digest function is `keccak256(observation)`.

## Composition in the ERC stack

OCP is the pre-execution input commitment layer in the TAWG ERC stack. Key composition patterns from group work:

- **Full on-chain chain**: 8281 `record()` (Base) → ERC-8294 AttestationIndex (mainnet) → ERC-8263 AnchorProof (mainnet). OCP commits the input; ERC-8263 commits the verdict separately.
- **WYRIWE layer above**: ERC-8299 WYRIWE proves what the model received; OCP proves when the input was committed before execution. The verifier checks whether to proceed.
- **Type-2 off-chain source auth**: `8281 (commit) + zkTLS (authenticate)` = source-authenticated inputHash. Commitment and source-authentication are two distinct jobs.
- **Agent architecture**: 8281 OCP commitment composes with ERC-8004 identity, ERC-8217 binding, and ERC-8299 WYRIWE so every agent action is recomputable from public chain data.

The current TAWG `/ledger` anchors via relay-seen + OTS/Bitcoin timestamping, not an on-chain OCP instance yet; OCP/8281 is the EVM-native target for the on-chain path.

## Security considerations

A commitment proves neither the truth of an observation nor who interpreted it correctly. Domain separation, canonical serialization, chain selection, and artifact availability remain critical. The recompute→compare→confirm invariant that OCP underlies was found to be missing attribution in a downstream README and required a post-hoc repair; explicitly citing 8281 lineage in composing specs avoids that repair cycle.

## Testing and examples

No registered test or example source was available at the time of last verification. A cross-SDK gap exists: the Rust 8281 implementation gates on its own inline golden rather than a shared canonical test vector for `keccak256(observation)`. A canonical `8281/observation-digest` cross-SDK vector is needed to prevent SDK divergence.

## Open questions

- Current evidence gaps: `normative_spec` and `test_or_example` are unregistered.
- Revocation and temporal validity require separately specified extensions.
- A canonical cross-SDK test vector for the OCP digest leg (`keccak256(observation)`) is outstanding.
